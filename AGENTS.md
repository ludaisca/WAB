## Development

Everything runs in Docker. Never install dependencies or databases on the host.

**Detect which mode you're in before running anything that touches Docker/Node** — this repo is worked on in two setups, and nothing else tells you which one is active:

- **Local mode**: the checkout and the Docker daemon are on the same machine.
- **Remote-server mode**: the checkout is an SFTP mount of a separate machine that runs the actual Docker daemon/stack — `rocky-server` is one example of such a machine, not the only one; a future remote could be a different box entirely. `Read`/`Edit`/`Write` work normally either way (it's just file I/O through the mount), but `docker compose`, `node_modules`, and the running containers only exist on the remote machine — running `docker compose` from the mounted path fails locally (bind-mounts break over the network filesystem layer).

Run this once per session to tell which applies:

```bash
findmnt -T . -no FSTYPE,SOURCE
```

- Local fstype (`btrfs`/`ext4`/`xfs`/`zfs`/...) → **local mode**.
- Network/FUSE fstype (`fuse.sshfs`/`nfs`/`cifs`/...) → **remote-server mode**. The `SOURCE` field is `user@host:/remote/path` — parse the remote host and path from it directly, never hardcode a name. (If `findmnt -T .` errors because the path isn't itself a mountpoint, run it against the repo root, or fall back to `stat -f -c '%T' .` for just the fstype.)

**In remote-server mode**, wrap every command that compiles, type-checks, lints, builds, or touches the running containers (including reading live data) in SSH, using the host/path you just parsed:

```bash
ssh <remote-host> "cd <remote-path> && docker compose exec app npx tsc --noEmit"
ssh <remote-host> "cd <remote-path> && docker compose exec app npm run lint"
ssh <remote-host> "cd <remote-path> && docker compose exec app npm run build"
ssh <remote-host> "cd <remote-path> && docker compose logs -f app"
```

Purely illustrative (do not hardcode elsewhere) — one real example seen on this repo: `<remote-host>` = `rocky-server`, `<remote-path>` = `/mnt/datos/Proyectos/WAB`. The stack (`wab-app-1`/`wab-db-1`/`wab-redis-1`, port 17100) on whatever the remote host turns out to be is the one with real data — don't `docker compose up` a second copy locally in this mode.

**In local mode**, run the same commands directly, no SSH wrapping:

```bash
docker compose up --build   # dev server + postgres + redis, hot reload, port 17100
docker compose down -v      # full teardown including volumes
npx tsc --noEmit            # type check
npm run build                # production build check
npx prisma generate          # after schema changes
```

Also in local mode: when testing the app from a browser or `curl`, use this machine's own hostname (`hostname`) or its Tailscale MagicDNS name (`tailscale status --json`, read `.Self.DNSName`/`.Self.HostName` — not `tailscale status --self`, that flag doesn't exist) — never `localhost`, never a hardcoded IP. If that hostname isn't already in `next.config.ts`'s `allowedDevOrigins`, add it and `docker compose restart app` (config changes aren't hot-reloaded) — see the `allowedDevOrigins` gotcha under "Framework quirks".

**Git is unaffected by either mode — never SSH-wrap it, and never skip it.** `git status`/`add`/`commit`/`push` always run directly against the checkout in place, local disk or SFTP-mounted, since git is just file I/O that the mount already handles transparently. Don't do `ssh rocky-server "cd /mnt/datos/Proyectos/WAB && git commit -m ..."` (unnecessary, and risks racing against the mount's own view of the index) — and don't reason "I'm on a remote mount, so I shouldn't commit here" and skip it. Commit exactly as you would in local mode.

- **docker-compose.yml** is production (used by Coolify). **docker-compose.override.yml** adds dev overrides (volumes, hot reload, env_file). Docker Compose merges both locally.
- `tailwindcss` and `@tailwindcss/postcss` are in `dependencies` (not devDependencies) — required at build time even with `NODE_ENV=production`.
- `public/` must contain `.gitkeep` — Docker BuildKit fails on `COPY` of empty directories.
- Named volume `media_data` mounted at `/app/media` (in both compose files) stores downloaded WhatsApp media binaries. `MEDIA_ROOT` env var defaults to `/app/media`; helpers in `lib/whatsapp/media-store.ts` resolve paths thoroughfully. `media/.gitkeep` exists on host for git tracking.
- Production `app` service uses `expose: 5000` (no fixed host port bind). Coolify's own proxy (Traefik) routes to it via the FQDN/domain configured in the Coolify UI. Do **not** add a hardcoded `ports:` mapping back to `docker-compose.yml` — a fixed host port causes `port is already allocated` failures on redeploy if a stale container from a previous deploy attempt (or another app) still holds that port on the server.

## Architecture: roles

Three roles with different UIs and access:

| Role | Sidebar | Routes blocked (`proxy.ts`) |
|---|---|---|
| `admin` | everything: Panel, Estadísticas, Chats, Contactos, Bots IA, Calificadores, Cuentas, Plantillas, Campañas, Usuarios, Reportes, Asistente IA, Backups, Config | none |
| `user` | like admin **minus** Contactos, Bots IA, Usuarios, Reportes, Asistente IA, Backups | `USER_BLOCKED`: `/whatsapp/contactos`, `/whatsapp/bots`, `/configuracion/ia`, `/asistente-ia`, `/configuracion/backups`, `/reportes` |
| `ejecutivo` | Chats, Contactos, Config | `EXECUTIVE_BLOCKED`: `/dashboard`, `/estadisticas`, `/usuarios`, `/whatsapp/{bots,campanas,plantillas,cuentas}`, `/configuracion/ia`, `/asistente-ia`, `/configuracion/backups`, `/reportes` |

Two pages were removed in the 2026-07 nav flattening: the `/whatsapp` hub (its KPIs duplicated Panel, its account list duplicated `/whatsapp/cuentas`; the route survives only as a `redirect("/whatsapp/cuentas")` and the nav item "Cuentas WhatsApp" points straight at `/whatsapp/cuentas`) and `/whatsapp/conocimiento` (fully redundant with the knowledge tab inside `whatsapp/bots/[id]`, which remains the only knowledge UI — its role-gating rides on `/whatsapp/bots`).

`/usuarios` is **not** middleware-blocked for role `user` — it's protected by nav-hiding plus the admin-only check in every `/api/usuarios` handler (403), so the page renders but loads nothing. Follow that same defense-in-depth shape (hide nav → block route where it matters → 403 in the API) when restricting anything new.

- First registered user auto-gets `admin` via atomic `$transaction(count + create)` in `app/api/auth/register/route.ts`. **The first user is always the admin and must never lose full access** — there are exactly these 3 roles, don't add/remove any without asking.
- Route protection in `proxy.ts` (Next.js 16 middleware) — `EXECUTIVE_BLOCKED` + `USER_BLOCKED` prefix lists.
- `dashboard-shell.tsx` builds `NAV[]` conditionally via `useSession().user.role`
- `/whatsapp/calificadores` is reachable by `user` but self-restricts client-side to only the "Leads calificados" tab (`canManageScorers = role !== "user"`) — the CRUD tab isn't a separate route, so it can't be blocked in `proxy.ts`.
- **AI config is admin-only in 3 layers**: the "Inteligencia Artificial" card on `/configuracion` renders only for admin, `/configuracion/ia` is in both blocked lists, and `GET/PATCH /api/configuracion/ia` return 403 for non-admin. `GET /api/configuracion/ia/models` deliberately stays open to all roles — `bots/_form.tsx` and `calificadores/_form.tsx` need it.
- **Account sharing (`WAAccountShare`)**: admin shares a `WAAccount` with another user from the "Compartir cuenta" card on `whatsapp/cuentas/[id]` (API: `GET/POST/DELETE /api/whatsapp/accounts/[id]/share`, admin-only). Sharing grants data visibility (chats/contactos/plantillas/campañas of that account) within what the grantee's role already permits — it does not change menu permissions.
- `lib/shared-accounts.ts` exports `getUserAccountIds(userId)` — own + shared accounts. Use in any new chat/message/template route that queries by account.
- **Account CRUD is admin-only**: `POST /api/whatsapp/accounts` and `PATCH`/`DELETE /api/whatsapp/accounts/[id]` return 403 for `user`/`ejecutivo` (GET stays open — they must still read the accounts shared with them). The UI hides "Agregar número", "Eliminar" and the App ID pencil for non-admins. Consequence: a non-admin's accounts always come from a `WAAccountShare`, never from their own creation.
- **Chat visibility by role (`WAAccount.hideUnattributedChats`, opt-in per account, default `false`)**: when on, roles `user` and `ejecutivo` only see that account's chats that have *attribution* — an outbound `WAMessage` with `campaignId` (mass campaign) or `leadSheetSourceId` (Sheets automation). Admin always sees everything. Toggle lives on the account detail page.
  - `lib/whatsapp/chat-visibility.ts` owns this. Two entry points: `chatAccessWhere(userId, role)` returns the **full** where fragment (accounts + visibility) and is what every per-chat route must use in place of the old `getUserAccountIds()` + `accountId: { in: … }` pair; `getChatVisibilityFilter(userId, role, accountIds)` returns just the restricting fragment (or `null`) for callers that already build their own `where` (the chat list, `dashboard/page.tsx`).
  - The attribution criterion is deliberately the same one behind `CHAT_ATTRIBUTION_MESSAGE_QUERY` in `chat-attribution.ts` (which paints the campaign badge). Change one and you must change the other, or a chat can show a campaign badge while being filtered out as unattributed.
  - **Applying it to the list only is not enough** — the 10 `chats/[chatId]/*` routes resolve a chat by id, and `messages/[messageId]/media` streams bytes by message id. All of them go through `chatAccessWhere()`; a new per-chat route that reaches for `getUserAccountIds()` instead is a hole. Exception, by design: the `/api/public/chat/[token]/*` routes behind the public share link (see "Public read-only chat link" below) intentionally skip `chatAccessWhere()` entirely — the token itself, not the session, is the access control.
  - In `/api/whatsapp/chats` the filter is pushed onto the same `messageFilters` array that feeds `where.AND` — assigning `where.AND` twice would silently drop the inbox's campaign/`hasReplied` filters.
- `Session.user` is typed with `id`, `email`, `name`, `role` (`types/next-auth.d.ts`). `createdAt` (ISO string) is also populated at runtime (`lib/auth.ts`) but is **not** part of that type — it's bolted on via an untyped cast (`(session.user as {createdAt?: string}).createdAt`), and every consumer must repeat the same cast (see `configuracion/page.tsx`).

## Framework quirks

- `proxy.ts` IS the middleware — Next.js 16 convention. Not `middleware.ts`
- `params` in page/layout props is `Promise<>` — must `await` before destructuring
- Server Components **cannot** pass Lucide/React components to Client Components as props. Error: "Functions cannot be passed directly to Client Components". Fix: convert the page to `"use client"` or render icons inside the client boundary. This includes `<Button icon={SomeIcon}>` written directly inside a Server Component — extract it into a small `"use client"` wrapper (e.g. `whatsapp/_add-account-button.tsx`) instead.
- `rm -rf .next` after adding/removing routes (stale Turbopack cache causes 404s/500s). If files are owned by Docker use `docker compose exec -u root app sh -c "rm -rf .next"` then `docker compose restart app`. **After a container recreate (e.g. adding a new volume), Turbopack's server-side chunk cache may not invalidate the client chunk unless you also do a hard refresh in the browser with DevTools "Disable cache" enabled** — HMR cannot bridge that gap; the client keeps loading the stale on-disk chunk with HTTP 200 (from disk cache) instead of asking for a fresh one.
- Pages using `useSearchParams()` must be wrapped in `<Suspense>`. See `app/(auth)/login/page.tsx` for pattern.
- Media URLs in chat UI are **server-proxied**, never raw Meta URLs. Always render `<img src=\`/api/whatsapp/messages/${msg.id}/media\`>` (or `<audio>`/`<video>`/download link). The endpoint authenticates via `getUserAccountIds` and streams bytes from `/app/media`. Never expose Meta's short-lived download URLs to the browser.
- `app/components/ui/modal.tsx`'s `visible` state must be initialized from the `open` prop (`useState(open)`), not `useState(false)` — the old code only flipped `visible` true on an `open: false→true` *transition*, so a modal mounted with `open={true}` from the start (e.g. reached via a `?param=1` URL instead of a button click) never became visible. Any new "auto-open via URL" modal pattern relies on this fix already being in place.
- Tailwind's `dark:` variant does **not** track this app's own light/dark toggle — this project uses a custom token system (`.light` class override on top of dark-by-default `:root` tokens in `app/globals.css`, no `@custom-variant dark` defined), so `dark:` falls back to Tailwind v4's default `prefers-color-scheme` media query, which reads the OS setting instead. Never use `dark:` classes; use the semantic tokens (`bg-surface`, `text-foreground`, etc.) which already respond correctly to the app's toggle. Exception: components that must always render in a *fixed* palette regardless of the app's theme (e.g. `<TemplatePreview>`, which mimics WhatsApp's own light chat UI) should hardcode their colors rather than use either `dark:` or the app's tokens.

### Server Components for top-level pages

`dashboard/page.tsx` and `estadisticas/page.tsx` are Server Components: they call `await auth()` + Prisma directly instead of `fetch()`-ing their own API routes (avoids a redundant HTTP round-trip). Reuse `getUserAccountIds()`/the same `where` clauses as the equivalent API route so the data scope doesn't silently diverge between the RSC and the JSON endpoint other pages still call.

Because `<Table>` (and any component using `render: (row) => JSX`) is `"use client"`, a Server Component **cannot** build its columns inline — that hits the "functions cannot be passed to Client Components" error. The fix used here: split into `page.tsx` (Server Component, fetches data) + `_view.tsx` (`"use client"`, receives the fetched data as a plain serializable prop and owns the `<Table>`/column definitions). See `estadisticas/page.tsx` + `estadisticas/_view.tsx`.

`lib/estadisticas/get-stats.ts` (`getEstadisticas(userId)`) feeds `estadisticas/page.tsx` directly (in-memory cache, 60s TTL, keyed by `userId`). The old `app/api/estadisticas` GET route was removed (2026-07) — it had no consumers; if an external integration ever needs stats over HTTP, re-add a thin route that calls `getEstadisticas()`. Global counters (accounts/chats/messages/bots/campaigns) shared by `/dashboard`, `/whatsapp` hub and `get-stats.ts` live in `lib/estadisticas/global-counts.ts` — always extend that module instead of re-writing the count queries inline, so the shared-accounts scope can't diverge between screens. `monthlyCost` reuses `lib/ai/budget.ts:getMonthlyAiCost()` (the same function that pauses spending) — never reimplement that aggregate.

RSC pages should have a sibling `loading.tsx` with skeleton placeholders — Next.js streams this automatically while the async page fetches data.

## Zona horaria (CDMX)

The server always runs in UTC (containers have no `TZ` set), but the business — budget month cutoffs, lead-recovery business hours, scheduled campaign sends, BullMQ cron ticks, and anything a user reads as "today"/"this month" — runs on `America/Mexico_City` wall-clock time. `lib/timezone.ts` (`MEXICO_CITY_TZ`) is the single place this conversion lives: `dateKeyInTz()`/`localHourInTz()` read a UTC instant as CDMX wall-clock, `startOfDayInTz()`/`startOfMonthInTz()` go the other way (CDMX calendar boundary → UTC instant), and `zonedDateTimeToUtc(dateStr, timeStr)` converts a picked date+time (campaign scheduling, etc.) the same way. **Never** use bare `Date` methods (`getHours()`, `getMonth()`, `toLocaleString()` without `timeZone`) for anything user-facing or month/day-bucketed — those read the *process's* zone (UTC in the container) or the browser's, never CDMX reliably. Consumers: `lib/ai/budget.ts` (monthly AI-spend cap boundary), `lib/whatsapp/lead-recovery.ts` (business-hours window), `lib/estadisticas/get-stats.ts` (daily/monthly buckets), `date-picker.tsx` ("today" for the calendar), `lib/whatsapp/chat-format.ts` (day dividers/bubble times, shared between the authenticated chat and the public `/c/[token]` link — using the same explicit zone on both sides of SSR avoids a hydration mismatch instead of just `suppressHydrationWarning`-ing it away), and campaign scheduling (`campanas/nueva/page.tsx` collects a separate date+time pair and converts via `zonedDateTimeToUtc`).

**BullMQ repeatable jobs must pass `tz: MEXICO_CITY_TZ` in their `repeat` option** (`lib/workers/index.ts`) — without it, `cron-parser` evaluates the pattern against the process's local zone (UTC), so e.g. `"0 2 * * *"` (meant as 2am CDMX) actually fired at 8pm CDMX the *previous* day. Every repeatable tick in this codebase now sets it explicitly; copy that pattern for any new one.

## Database

### Schema
`prisma/schema.prisma` — 41 models (`SystemReport` added 2026-08 for the Reportes feature, see "Reportes" below). Key relationships: `User → WAAccount[]`, `User → AppSettings (1:1)`, `WABot ↔ WABotKnowledge (M:N via WABotKnowledgeBot)`, `WAAccount → WAAccountShare[] → User`, `WAChat → Contact (1:1)`, `Contact ↔ Tag (M:N via ContactTag)`, `User → WALeadScorerBot[]`, `WAChat → WALeadScore[] ← WALeadScorerBot` (one score per `(chatId, scorerId)` pair, see "Lead scoring" below), `WAChat → WALeadRecoveryAttempt[]` (see "Lead recovery" below). `WAMessage` carries all media metadata: `messageType` (`text`/`image`/`audio`/`video`/`document`/`sticker`), `caption`, `mediaId` (Meta id), `mediaUrl` (relative path under `MEDIA_ROOT`), `mimeType`, `filename`, `bytesSize` (`width`/`height`/`duration` were dropped 2026-07 — Meta's webhook never populated them). `body` is reused for both text and caption-derived text; `caption` is the dedicated caption field.

### Commands
```bash
npx prisma db push       # sync schema → DB (dev, creates columns)
npx prisma generate      # regenerate client after schema changes
prisma migrate dev        # create a migration (preferred for production changes)
```

### pgvector
PostgreSQL image is `pgvector/pgvector:pg16`. Extension enabled via `docker/init.sql`. Vector column is `vector(768)` — the only provider produces 768-dim embeddings (Google `gemini-embedding-2` — `text-embedding-004` was retired; it defaults to 3072 dims and is truncated to 768 via `outputDimensionality`, see "AI providers" below).

**IVFFlat index gotcha**: `docker/init.sql` only runs once, at Postgres's *first* volume init — before `prisma db push` has created `wa_bot_knowledge`, so a `CREATE INDEX` there fails silently (table doesn't exist yet) and never gets a second chance. The index is instead created by `prisma/sql/ensure-vector-index.sql`, run via `npx prisma db execute --file ... ` *after* `db push`/`migrate deploy` in both `scripts/startup.sh` (prod) and `docker-compose.override.yml` (dev command). If RAG search feels like it's doing a full table scan, check `SELECT indexname FROM pg_indexes WHERE tablename = 'wa_bot_knowledge'` for `idx_knowledge_embedding` before assuming it's a query problem.

### Raw SQL gotcha
Prisma `$queryRawUnsafe` uses actual DB column names. Fields without `@map` use the Prisma field name as-is (camelCase). Prefer Prisma query builder over raw SQL.

### Registration
Uses `prisma.$transaction()` for atomic `count() + create()` — prevents race condition where two simultaneous registrations both get `admin`.

## Redis + BullMQ

16 queues, auto-started via `instrumentation.ts`:

| Queue | Concurrency | Trigger |
|---|---|---|
| `bot-messages` | 3 | `ingestInboundMessage()` detects active bot → enqueues |
| `campaign-send` | 1 | "Enviar" on campaign, **plus** a repeatable `scheduled-tick` job (`* * * * *`, every minute) that claims due `SCHEDULED` campaigns (`processScheduledCampaignsTick()`, atomic `updateMany` on status so overlapping ticks can't double-enqueue), **plus** a repeatable `stuck-tick` job (`*/10 * * * *`) that re-enqueues any campaign stuck in `SENDING` with `PENDING` recipients and `sentAt` older than 20 min (`processStuckCampaignsTick()` — recovers from the process dying between the `SENDING` DB write and the BullMQ `add()`, or mid-send; safe to re-run since `processCampaignJob()` re-reads current `PENDING` recipients and recomputes counts instead of accumulating) — the worker branches on `job.name`. All three enqueue paths (`sendCampaign()`, both ticks) share a deterministic `jobId` of `campaign-send-<campaignId>` so BullMQ dedupes if more than one path tries to claim the same campaign |
| `rag-index` | 2 | User uploads knowledge document |
| `media-download` | 5 | `ingestInboundMessage()` with Meta `mediaId` → downloads binary bytes async. `attempts: 5` (only queue overriding the default `attempts: 3`) |
| `audio-transcribe` | 3 | `media-worker.ts` enqueues after an inbound **audio** message's bytes land on disk (never a race: the job always sees `mediaUrl` set) → transcribes the voice note with Gemini using the user's `defaultModel`, persists `WAMessage.transcription` and logs an `AudioTranscriptionUsage` row. Skips silently without an API key / when the monthly budget is exceeded / if the file was purged by `media-cleanup` — transcription is a UX extra, never a critical path |
| `media-cleanup` | 1 | Self-scheduled: `startWorkers()` registers a repeatable job (`repeat: {pattern: "0 3 * * *"}`, daily at 3am) on boot — not triggered by user action |
| `bot-message-send` | 5 | `bot-worker.ts` when `WABot.humanizeEnabled` is on — delivers each split chunk of a "humanized" reply as its own delayed job |
| `lead-scoring` | 1 | Self-scheduled repeatable tick (`*/5 * * * *`) — scheduled scorer runs, see "Lead scoring" |
| `lead-recovery` | 1 | Self-scheduled repeatable tick (`*/15 * * * *`) — re-engages silent leads, see "Lead recovery" |
| `sheets-sync` | 1 | Self-scheduled repeatable tick (`*/15 * * * *`, `lib/workers/sheets-sync-worker.ts`) — runs every enabled `SheetExport` per user, see "Google Sheets" export section |
| `lead-sheet-import` | 1 | Self-scheduled repeatable tick (`*/5 * * * *`) — imports/sends leads from a connected `LeadSheetSource` (Sheets-based campaign automation), throttled between accounts to avoid bursting the Graph API |
| `template-sync` | 1 | Self-scheduled repeatable tick (`*/15 * * * *`, `lib/workers/template-sync-worker.ts`) — refreshes `WATemplate.status` unattended for every account with `wabaId`+`accessToken`, independent of the manual "Sincronizar" button on `/whatsapp/plantillas` |
| `agent-action-expiry` | 1 | Self-scheduled repeatable tick (`*/15 * * * *`) — flips `AgentAction` rows stuck `PENDING` past their `expiresAt` (24h) to `EXPIRED`, see "AI assistant (Asistente IA)" |
| `system-diagnostics` | 1 | Self-scheduled repeatable tick (`0 * * * *`, hourly, `lib/workers/system-diagnostics-worker.ts`) — scans each user's accounts/bots/scorers via `lib/whatsapp/system-diagnostics.ts`, creates a `SYSTEM_ISSUE` notification per new "alta" severity finding (deduped 6h per title) |
| `system-backup` | 1 | Manual ("Generar respaldo ahora" on `/configuracion/backups`) **plus** a daily repeatable tick (`0 2 * * *`) — see "Backups & disaster recovery" |
| `system-restore` | 1 | Manual restore trigger only. `attempts: 1`, deliberately no BullMQ retry — see "Backups & disaster recovery" |
| `report-generate` | 2 | Manual only ("Generar reporte" on `/reportes`) — no repeatable tick, v1 is manual-generation-only. Default `attempts: 3` is safe here (unlike restore): the job only reads data, so a retry after a transient failure has no destructive side effect — see "Reportes" |

No queue in this table has a per-job execution timeout — BullMQ 5.x's `JobsOptions` type has no `timeout` field, so a `timeout` previously set in `lib/queue.ts` did nothing and was removed; throughput is governed only by `concurrency` per worker and BullMQ's own stalled-job detection. `system-backup`/`system-restore` are the exception in spirit but not mechanism: their pipeline functions (`lib/backup/create-backup.ts`, `restore-backup.ts`) pass `BACKUP_TIMEOUT_MS` (default 30 min) as the `timeout` option to each `execFile` subprocess call (`pg_dump`/`pg_restore`/`prisma db push`) — that's a Node child-process timeout internal to the job's own code, not a BullMQ job option.

- `media-cleanup-worker.ts:processMediaCleanupJob()` deletes `WAMessage.mediaUrl` files older than `MEDIA_RETENTION_DAYS` (env var, default 90) and clears the column, keeping the `media_data` volume bounded. No-ops if `MEDIA_RETENTION_DAYS <= 0`.
- **Bot reply humanization** (`WABot.humanizeEnabled`, opt-in, default `false`): when on, `bot-worker.ts` splits the reply on blank lines (`lib/whatsapp/humanize.ts:splitReply()`) and enqueues each chunk on `bot-message-send` with a cumulative simulated-typing delay (`computeTypingDelay()`, ~40ms/char, capped 0.8–8s) instead of calling `sendWhatsAppMessage()` synchronously — keeps the main `bot-messages` job from holding its concurrency slot for the whole send sequence. `bot-send-worker.ts:processBotSendJob()` re-fetches the `WAAccount` and does the actual send + `WAMessage`/`WAChat` bookkeeping per chunk. Tone/pacing only — never use this to imply the chat isn't automated (WhatsApp's Business Messaging Policy expects disclosure where applicable).
- Workers live in `lib/workers/`. Queue definitions in `lib/queue.ts`.
- `REDIS_URL` env var required.
- `defaultJobOptions` include `attempts: 3`, `backoff: exponential`, `removeOnComplete: 100`, `removeOnFail: 50`.
- Workers have graceful shutdown on `SIGTERM`/`SIGINT`.
- `lib/redis.ts` exports `getRedisClient()` — singleton with retry strategy. Use this, not new connections.
- `lib/rate-limit.ts` — sliding-window rate limiter with Redis + in-memory fallback (fail-safe). Add to any new auth-sensitive endpoint.

## AI providers

One provider: `google` (native Gemini SDK) — OpenRouter was removed in 2026-08 (schema, provider client, `openai` dep and the provider select all deleted; legacy rows/columns backfilled by `prisma/sql/migrate-off-openrouter.sql` run in `scripts/startup.sh` before `db push`, and post-restore in `lib/backup/restore-backup.ts`). API keys stored **per-user** in `AppSettings.googleApiKey`, not per-bot. Encrypted with AES-256-GCM (`lib/crypto.ts`). `getUserApiKey(userId)`/`getAIProvider(apiKey)` no longer take a provider argument.

Provider clients in `lib/ai/providers/`. Factory in `lib/ai/factory.ts`.

- **Multimodal in/out**: `AIMessage.content` is `string | ContentPart[]` where `ContentPart` is `{type:"text",text}`, `{type:"image_url",image_url:{url}}` or `{type:"audio_url",audio_url:{url}}`. Both providers forward arrays natively. The Google provider maps `image_url`/`audio_url` with a `data:` URI base64 into `inlineData: {mimeType, data}`; plain URLs (non-data-URI) are NOT supported inside inlineData — bot-worker always builds data-URI from local bytes. **Audio input is Gemini-only** (`bot-worker.ts` gates `isAudio` on `provider === "google"`; OpenAI's chat shape has no generic audio part). **Documents** (PDF/`text/*`) are provider-agnostic: `lib/whatsapp/extract-document-text.ts` extracts text server-side (max 6000 chars) and injects it as a plain text part. Bot reply stays text-only (media input, no media output).
- **Embedding dimension**: 768 (Google `gemini-embedding-2` — `text-embedding-004` was retired — defaults to 3072 dims and is truncated to 768 via the `outputDimensionality` request param, Matryoshka Representation Learning, see `lib/ai/providers/google.ts`).
- **Google usage**: `usageMetadata` on `response` object provides `promptTokenCount`, `candidatesTokenCount`. Must be returned in `AICompletionResponse.usage`.
- **Google `systemInstruction` gotcha**: must be passed to `genAI.getGenerativeModel({ model, systemInstruction })`, never to `.startChat({ systemInstruction })`. The SDK (`@google/generative-ai`) only runs its string→`Content` formatting on the value passed to `getGenerativeModel`; passing it to `startChat` instead silently overrides the formatted value with the raw unformatted one and the REST API rejects it with a 400 on `system_instruction`. **Caveat**: only a `string` `systemInstruction` is supported by the v1 SDK path — if you pass it parts/array, the formatter will mangle it. Always send a plain string for the system prompt even when the rest of the conversation is multimodal. The provider **concatenates all `system`-role messages** (`join("\n\n")`) into that single `systemInstruction` — the pipeline sends several (wrapped user prompt, RAG context, guardrail, campaign note) and an earlier version silently dropped all but the first.
- Model pricing in `lib/ai/pricing.ts` (USD per 1M tokens). `estimateCost()` is async — **Google has no pricing API**, so its entries in the static table are hand-maintained (last verified 2026-07-15); a Google model missing from the table logs cost $0 with a console warning, so add pricing when adopting a new Gemini model or `WABotUsage.estimatedCost`/the budget silently undercount. Usage logged per interaction in `WABotUsage`.
- Model lists are fetched live from Google (`lib/ai/models.ts`, exposed via `GET /api/configuracion/ia/models`) rather than hardcoded — the catalog changes. Bot creation and default-model settings both use this with a small static fallback list if the fetch fails.
- RAG: documents chunked → embeddings generated → stored in pgvector → searched with cosine similarity (`<=>` operator).
- **Vision model cost**: each image in context ≈ +800-1500 tokens. Bot history is text-only (no past images forwarded); only the *current* user image becomes an `image_url` part in the `user` turn. The worker re-reads `WAMessage.mediaUrl` from DB if the Meta download job hasn't finished populating the local path yet.
- **Vision capability check**: there's no enforced gate on per-model vision capability — if a model isn't vision-capable it will error on the multimodal turn, which the bot-worker catch sets `WABot.status: "ERROR"` (same as any other AI failure). Currently known vision-capable models: Gemini 1.5/2.0 Flash/Pro.
- **Lead scorer bots** (`WALeadScorerBot`) reuse the same provider/model/API-key plumbing as `WABot` (own `provider`+`model`+`systemPrompt`, resolved via the same `getUserApiKey()`) but score a conversation on demand instead of replying to it — see "Lead scoring" under CRM below.
- **User-configured system prompts are wrapped, not sent raw**: `lib/ai/prompt-sanitizer.ts:wrapUserPrompt()` frames both `WABot.systemPrompt` (`bot-worker.ts`) and `WALeadScorerBot.systemPrompt` (`score/route.ts`) inside a delimited `<user_instructions>` block with an explicit "treat as data, not instructions" preamble and a length cap (12000 chars, `console.warn`s if a prompt is actually truncated — raised 2026-07 from an earlier silent 4000 that was cutting a detailed sales-funnel prompt off mid-sentence, dropping whole trailing sections including the humanization line-break instruction) — mitigates prompt injection against the system messages that follow (RAG context, memory summary, the scorer's JSON contract). The scorer's JSON contract also now asks for a fenced ` ```json ` block; `parseScoreResponse()` tries that first and falls back to the old greedy `{...}` regex for models that ignore the fencing instruction. `prompt-sanitizer.ts` also exports `SCOPE_GUARDRAIL` — a fixed system message (priority over `<user_instructions>` and any user/media content) appended by `bot-worker.ts` and `lib/whatsapp/lead-recovery.ts`; include it in any new AI flow that converses with end users.
- ~~Model list race on provider switch~~ (removed 2026-08 with the provider select — there's a single provider now; the model lists fetched in `configuracion/ia/page.tsx`, `bots/_form.tsx` and `calificadores/_form.tsx` are always Google's).

### Bot tool-calling: price lookup + sondeo tracking

`lib/whatsapp/bot-tools/generate-reply.ts:generateBotReply()` is the single place a bot's turn gets assembled — system prompt + RAG context + tool-calling + anti-hallucination guardrails — used identically by the real send path (`lib/workers/bot-worker.ts`) and by the persistent test-conversation panel (`app/api/whatsapp/bots/[id]/test/conversations/**`, `WABotTestConversation`/`WABotTestMessage` — replaced the old single-shot, no-RAG-no-tools `/test` endpoint in 2026-07, so "Probar" a bot now reflects exactly how it'll behave for a real lead). `lib/whatsapp/bot-tools/run-tool-loop.ts:completeWithBotTools()` bounds the tool-calling loop at `BOT_MAX_TOOL_ITERATIONS = 4` (forces a final tool-free completion on the last iteration) — a live customer turn, unlike the Asistente IA's up-to-8-round loop, needs to stay fast; raised from 3 once a second always-on tool made 2 tool round-trips per turn common.

Two tools, both built per-turn in `generateBotReply()`:
- **`consultar_precio_producto`** (`price-lookup.ts`) — opt-in via `WABot.priceLookupEnabled`/`priceLookupUrl`/`priceLookupParam`/`priceLookupExtraQuery`. Calls a GET price API (`lib/http/fetch-with-timeout.ts`, 8s timeout) and returns only a server-computed `precioApartirDe` (max of the API's `callamount`/`promotionprice`) — never the raw API JSON — so the model can't cite the wrong field or the lower of the two prices. `WABot.priceLookupSkus` (curated `"CODE | label"` lines, one per line) is optional: non-empty restricts the tool to those exact codes (rejected before hitting the network) and is spelled out verbatim in the tool description; empty falls back to letting the model supply any code it believes it knows from RAG.
- **`registrar_dato_prospecto`** (`qualified-data.ts`) — always available (not opt-in, no per-bot config), a generic free-form `{clave, valor}` key/value store for whatever qualifying/probing data *that bot's own* systemPrompt cares about (name, budget, decision-maker, etc. — deliberately no fixed schema, since each bot's sondeo methodology differs). Completely silent to the lead — the tool description explicitly forbids the model from mentioning it ("ya registré...") after a live test run leaked exactly that. Persisted per-conversation on `WABotConversation.qualifiedData` / `WABotTestConversation.qualifiedData` (`Json`, merged not replaced on each call), independent of `memoryType`. `generateBotReply()` also injects an objective reply-count system note every turn ("llevas N respuestas") — conditions like "reveal price only after your 2nd reply" are unreliable for a model to self-assess by re-scanning raw history alone.

**Anti-hallucination backstops** (also in `generate-reply.ts`, run *after* the model's final text): a regex catches an ungrounded price (currency symbol/word + digits) and swaps in a fixed hand-off line, unless RAG actually matched this turn or the price tool returned `found: true`; a second regex does the same for any URL that doesn't appear verbatim in the system prompt/RAG/tool results from this turn. A third check catches the model returning empty `content` (can happen on the forced tool-free final iteration if it was mid tool-call reasoning) and substitutes a fixed hold message instead of silently sending/saving nothing. None of the three guard against a fabricated *product name/model* in free text — deliberately, the format's too open for a reliable regex; that risk is mitigated only by RAG actually being populated for what the bot claims to sell and by the price tool's curated SKU list.

## AI assistant (Asistente IA)

Admin-only internal ops copilot at `/asistente-ia`, distinct from the customer-facing `WABot`/`WALeadScorerBot`: it's a natural-language chat for querying/operating the CRM itself (e.g. "¿cuántos leads calificados como oportunidad tengo esta semana?", "apaga el bot de Ventas Norte"), not something an end lead ever sees. Fully reuses the `lib/ai/` provider plumbing described above (`getAIProvider()`, `getUserApiKey()`, `estimateCost()`, `isMonthlyBudgetExceeded()`/`checkBudgetAlert()`) — its spend is tracked separately in `AgentUsage` but counts toward the **same** monthly AI budget as bots/scorers/lead-recovery. There is no separate provider/model setting for it — it always uses the admin's global `AppSettings.defaultProvider`/`defaultModel`.

- **Admin-only in the same 3-layer shape as `/configuracion/ia`**: `/asistente-ia` is in `PROTECTED`, `EXECUTIVE_BLOCKED` and `USER_BLOCKED` in `proxy.ts`; both `app/(dashboard)/asistente-ia/page.tsx` and `.../auditoria/page.tsx` also redundantly redirect non-admins server-side; every route under `app/api/agent/**` 403s non-admins independently.
- **Three-tier tool risk model** (`lib/agent/tools/types.ts`, `ToolRiskTier`), enforced per-tool, not per-request: `READ` tools run inline and leave no audit row; `MINOR` tools run inline immediately but write an `AgentAction` row (`status: "EXECUTED"`, or `"FAILED"` + `errorMessage` on throw) purely for audit; `CONFIRM` tools execute **nothing** at proposal time — the orchestrator writes an `AgentAction` with `status: "PENDING"` and `expiresAt` 24h out, plus a UI-marker `AgentMessage` so `AgentActionCard` (`app/components/ui/agent-action-card.tsx`) renders inline in the chat with Confirmar/Rechazar buttons. Nothing happens until the admin clicks one.
- Tools live one file per domain in `lib/agent/tools/` (`accounts.ts`, `bots.ts`, `budget.ts`, `campaigns.ts`, `chats.ts`, `contacts.ts`, `diagnostics.ts`, `scorers.ts`, `sheet-sources.ts`, `tags.ts`, `templates.ts`), registered in `registry.ts`, arguments validated against each tool's JSON Schema in `validate.ts` before dispatch. The system prompt (`lib/agent/system-prompt.ts`) hard-codes scope limits that have no corresponding tool at all: it never sends WhatsApp messages to leads/clients, never edits code, never manages users/roles, never touches account credentials (access token/app secret/verify token). It also enforces that `Contact.leadStatus` (CRM funnel, settable via a MINOR tool) and AI-scorer output (`frio`/`interesado`/`oportunidad`/etc., read-only) stay conceptually separate — the model is told not to fake one by writing the other.
- **CONFIRM tools re-validate at execution time, not just proposal time**: `POST /api/agent/actions/[id]/confirm` atomically claims the row (`updateMany` on `{status: "PENDING", expiresAt: {gt: now} OR null}` → `"EXECUTED"`, 409 if the claim matched zero rows — guards against double-click and against confirming something already expired), then calls the tool's `executeConfirm()`, which re-checks its own preconditions (bot still exists, campaign still `DRAFT`, template still `APPROVED`, etc.) since real state may have drifted since the model proposed the action. `POST /api/agent/actions/[id]/reject` does the equivalent atomic claim straight to `"REJECTED"`.
- **Expiry**: the `agent-action-expiry` queue (see "Redis + BullMQ" above) flips stale `PENDING` rows to `"EXPIRED"` every 15 minutes — same mechanism already documented there, no separate worker logic to know about.
- Prisma models: `AgentConversation` (per-admin, has `messages[]`/`actions[]`/`usage[]`), `AgentMessage` (`role: AgentRole` = `USER`/`ASSISTANT`/`TOOL`; `toolCalls Json?` on assistant turns so the transcript can be replayed to the provider; a `TOOL` row with `actionId` set is a pending-CONFIRM UI marker, skipped when rebuilding the provider transcript), `AgentAction` (`status: AgentActionStatus` = `PENDING`/`EXECUTED`/`REJECTED`/`EXPIRED`/`FAILED`), `AgentUsage` (tokens + `estimatedCost` + `toolCallCount` per model call).
- Orchestrator: `lib/agent/orchestrator.ts:handleUserMessage(conversationId, userId, userText)` — short-circuits with a Spanish message (no model call) if the monthly budget is exceeded or no API key is configured; otherwise loops up to `MAX_ITERATIONS = 8` tool-call rounds per user turn, forcing `toolChoice: "none"` on the last allowed iteration so the model always ends with a text answer instead of looping forever.
- API routes (`app/api/agent/**`, all admin-only): `conversations` GET/POST, `conversations/[id]` GET/DELETE, `conversations/[id]/messages` POST (drives the whole turn, auto-titles the conversation from the first message), `actions` GET (filterable by status/riskTier/date — exists but the Auditoría UI currently reads `AgentAction` directly via Prisma in the server component instead of calling it), `actions/[id]/confirm` POST, `actions/[id]/reject` POST.
- UI: `app/(dashboard)/asistente-ia/page.tsx` — chat thread + conversation sidebar. `.../auditoria/page.tsx` — read-only log of the admin's own `AgentAction` rows (tool, risk tier, status, resolved-by, timestamp), client-filterable by status/riskTier.

## Encryption

AES-256-GCM with random 12-byte IV + 16-byte auth tag. Format: `hex(iv):hex(authTag):hex(ciphertext)`. Key from `ENCRYPTION_KEY` env var (64 hex chars = 32 bytes generated via `openssl rand -hex 32`).

Fields encrypted at rest: `WAAccount.accessToken`, `WAAccount.appSecret`, `AppSettings.googleApiKey`, `GoogleAccount.accessToken`/`refreshToken`, `SystemConfig.s3SecretAccessKey`.

## Backups & disaster recovery

Full-system backup/restore (Postgres + media), independent of Coolify/host-level backups — lives entirely in `lib/backup/`, driven by two BullMQ queues (`system-backup`, `system-restore`, see "Redis + BullMQ"), admin-only UI at `/configuracion/backups` (`_view.tsx` for history/actions, `_storage-form.tsx` for the S3/R2 config below), all routes under `app/api/configuracion/backups/**`.

- **Pipeline** (`lib/backup/create-backup.ts:runBackupPipeline`): `pg_dump -Fc --exclude-table=system_backups --exclude-table=system_restore_logs` (excluding those two tables is deliberate — including them would self-reference a half-written row of the very backup being created, corrupting a future restore's own history) + `archiveMedia()` tars `MEDIA_ROOT`, both checksummed (`sha256File`) into a `manifest.json` (schema hash, Postgres version, `ENCRYPTION_KEY` fingerprint, table row counts) — the three files get tarred together (uncompressed outer layer, so `manifest.json` stays peekable without decompressing everything) into `BACKUP_ROOT/backup-<ISO ts>-<type>-<id>.tar`. `SystemBackup.type` is `MANUAL` (button) / `SCHEDULED` (daily `0 2 * * *` tick) / `PRE_RESTORE` (auto safety snapshot taken right before any restore runs, see below).
- **Restore** (`lib/backup/restore-backup.ts:runRestorePipeline`): validates checksums+manifest → enters maintenance mode (`lib/system-maintenance.ts`, pauses all BullMQ workers + makes the webhook return 503) → takes a fresh `PRE_RESTORE` safety backup of the *current* state → `pg_restore --clean --if-exists --single-transaction --exit-on-error` → `prisma db push --accept-data-loss` to reconcile schema drift → swaps `MEDIA_ROOT` via a staging/rename dance → exits maintenance → notifies admins. Requires typing `RESTORE_CONFIRMATION_PHRASE` ("RESTAURAR TODO", `lib/backup/constants.ts`) client-side, re-validated server-side. `system-restore`'s worker runs with `attempts: 1` — no BullMQ auto-retry, on purpose: retrying a job that already failed mid-restore is exactly the kind of silent, destructive behavior to avoid; a failure needs a new explicit admin action.
- **Retention** (`lib/backup/retention.ts:purgeOldBackups`, runs after every non-`PRE_RESTORE` backup): keeps the `BACKUP_RETENTION_COUNT` (default 7, env var) most recent `MANUAL`+`SCHEDULED` `COMPLETED` rows, deletes the rest (file + row + S3 object if any). `PRE_RESTORE` backups are never auto-purged — manual delete only, they're the safety net. Also reconciles orphaned `.tar` files and stale upload-for-restore files (>24h).
- **Restore source**: either `HISTORY` (an existing `SystemBackup`) or `UPLOADED` (streamed straight to disk via `lib/backup/upload.ts:streamUploadToFile`, never buffered in memory — enforced against `MAX_RESTORE_UPLOAD_BYTES`, default 5GB, both via `Content-Length` and live byte count).
- **S3/R2 off-container storage** (`lib/backup/s3-storage.ts`, opt-in, configured entirely from the UI — no env vars, so an admin can turn it on/off without a redeploy): config lives on the `SystemConfig` singleton (`s3Enabled`/`s3Endpoint`/`s3Region`/`s3Bucket`/`s3AccessKeyId`/`s3SecretAccessKey` encrypted/`s3ForcePathStyle`), edited via `GET/PATCH /api/configuracion/backups/storage` (masked-secret pattern, same shape as `configuracion/ia`) with a "Probar conexión" button (`POST .../storage/test`, `HeadBucketCommand` falling back to a `PutObject`+`DeleteObject` probe since some R2 tokens scoped to object-level permissions reject `HeadBucket`). Every completed backup gets uploaded (`@aws-sdk/lib-storage`'s `Upload` — streaming multipart, never a single in-memory `PutObject`, since these tars can be multi-GB) and the object key stored on `SystemBackup.s3Key`; a failed upload does **not** fail the backup (the local copy is already valid) — it's recorded in `s3UploadError` instead. `ensureLocalBackupFile()` is the single chokepoint that makes local-vs-S3 transparent to every reader (download route, restore preview, restore trigger, and the restore pipeline itself): if the local `.tar` is missing (e.g. the Docker volume was lost), it transparently downloads from S3 first. Local files are **never** deleted after a successful S3 upload — S3 is additive durability, not a replacement (the pipeline still needs local disk to operate).
- **Separate from this**: `app/api/configuracion/backups/export/route.ts` is a different, lighter per-entity CSV/JSON export (not a restorable `.tar`) — don't conflate the two.

Env vars: `BACKUP_ROOT` (default `/app/backups`), `BACKUP_RETENTION_COUNT` (default 7), `BACKUP_TIMEOUT_MS` (default 1800000), `MAX_RESTORE_UPLOAD_BYTES` (default 5368709120).

## Reportes

Admin-only business-report generator at `/reportes` (2026-08) — a downloadable "todo incluido" `.xlsx` for an arbitrary date range, plus a live dashboard scoped to that same range. Distinct from the system-level `.tar` backups above: no S3, no manifest/checksums, no `SCHEDULED`/`PRE_RESTORE` types (v1 is manual-generation-only, no repeatable tick), and `SystemReport.sizeBytes` is a plain `Int` (a business `.xlsx` never approaches the ~2.1GB `BigInt` threshold `SystemBackup.sizeBytes` needs).

- **Pipeline** (`lib/reports/generate-report.ts:runReportPipeline`): the `SystemReport` row already exists with `status: "PENDING"` (created by `POST /api/reportes`, rate-limited 10/hour/admin, `dateFrom`/`dateTo` capped at `MAX_REPORT_RANGE_DAYS` = 400) before the job runs — the worker flips it to `RUNNING`, calls `buildReportWorkbook()` (`lib/reports/build-workbook.ts`), writes the `.xlsx` to `REPORTS_ROOT` (default `/app/reports`, own named volume `report_data`), and flips to `COMPLETED`/`FAILED`. The picked CDMX dates convert to an exact UTC `[gte, lt)` pair via `lib/reports/date-range.ts:reportRangeToUtc()` (same explicit-timezone pattern as the rest of the app, see "Zona horaria (CDMX)").
- **13 sheets** built by `buildReportWorkbook()`: Resumen, Mensajes diarios, Mensajes por tipo, Bots y costo IA, Costos IA detallado, Campañas, Plantillas, Leads calificados, Chats, Contactos, Rendimiento agentes, Cuentas, Etiquetas, Diagnóstico. "Leads calificados"/Campañas/Chats/Contactos reuse the SAME `buildLeadScoreRows`/`buildCampaignResultRows`/`buildChatRows`/`buildContactRows` builders from `lib/google/dataset-queries.ts` that also feed the Google Sheets export integration and the manual CSV export — one dataset definition, three delivery mechanisms.
- **Date-range gotcha**: those 4 reused builders interpret a `dateFrom`/`dateTo` string as UTC midnight internally (`dataset-queries.ts`'s own private `dateRange()`), not CDMX — a ~6h drift against what the admin actually picked. `build-workbook.ts` works around this by NOT passing the exact range to those builders at all: it fetches with `widenedDateStrings()` (`date-range.ts`, ±1 day margin, still UTC-interpreted so it's guaranteed to over-include) and then trims precisely in JS via `inRange()` (CDMX-exact, using `zonedDateTimeToUtc`).
- **Live dashboard** (`GET /api/reportes/dashboard?dateFrom=&dateTo=`, `lib/reports/queries/dashboard.ts:getReportDashboard`, rendered by `_dashboard.tsx`): a *separate*, lighter set of aggregate-only queries (`groupBy`/`aggregate`/capped `findMany`, never the row-building dataset functions above) scoped to the exact chosen range — KPIs (messages, chats, contacts, AI cost/tokens, leads calificados), a daily message trend chart, a campaign funnel, top-5 bot costs, and a diagnostics summary (reuses `runSystemDiagnostics()` from `lib/whatsapp/system-diagnostics.ts`, the same scan behind the `system-diagnostics` queue). Also includes lead-qualification analytics beyond what the `.xlsx`'s "Leads calificados" sheet shows per-row: `qualifiedAvgScore`, `qualifiedConversionRate` (% of non-`descartado` leads reaching `oportunidad`+), `qualificationFunnel` (cumulative depth: Calificados → Interesado+ → Oportunidad+ → Prioridad alta, rendered with `FunnelBars`), `qualificationTrend` (daily series by label via `TrendChart`, both from `app/components/ui/chart.tsx`), and `leadFindings` (top-5 by frequency of `producto_interes`/`objeciones_dudas`/`senales_compra`/`urgencia` from `WALeadScore.details` — the first place those free-text fields get aggregated instead of only shown lead-by-lead in the detail modal/export). All of it counts *evaluations* in range (`WALeadScore.updatedAt`), not deduplicated chats — same semantic as the pre-existing `leadsByLabel`/"Leads calificados — {label}" rows in the Resumen sheet, so the on-screen dashboard and the exported `.xlsx` never diverge on this. (A near-identical set of aggregates was first prototyped in `/estadisticas` on a fixed 14-day rolling window, then moved here — `/reportes` is the correct home since it's already scoped to the exact date range a "leads calificados" analysis actually needs, and the fixed window in Estadísticas had no relationship to it.)
  - **Perf gotcha, learned the hard way**: this route used to call the shared `fetchMessagesInRange` (unbounded `findMany`, every message row) for the KPI totals — fine for the background `.xlsx` job (no request-latency pressure) but disastrous for this *interactive* route once an account had tens of thousands of messages (11-22s per request, looked exactly like "the dashboard doesn't update"). Fixed by splitting into `fetchMessageCounts()` (`lib/reports/queries/messages.ts`, a `groupBy`, exact totals, ~30ms regardless of table size) and `fetchDailyMessageTrend()` (capped `take: 5000`, same trade-off `get-stats.ts`'s own `dailyMessages` already accepts — the trend chart is directional, doesn't need every row). Never call `fetchMessagesInRange` from an interactive route again; it exists only for `build-workbook.ts`.
- **`fetchChatAttributions()` gotcha** (`lib/whatsapp/chat-attribution.ts`): `buildChatRows`/`buildLeadScoreRows` used to nest `messages: CHAT_ATTRIBUTION_MESSAGE_QUERY` (the campaign/lead-source attribution lookup, negation filters `campaignId: {not: null}` OR `leadSheetSourceId: {not: null}`) directly inside their `findMany`'s `select`. Prisma loads a filtered to-many relation like that via a separate batched `chatId IN (...)` query, and refuses to auto-split that batch when negation filters are present — it throws "Query parameter limit exceeded ... negation filters used prevent the query from being split" once the parent result set gets into the thousands (hit this for real against a 47k-chat account, on the very first attempt to export a report with no date-range narrowing it down). Fixed by computing attribution as a *separate* step: `fetchChatAttributions(chatIds)` batches the `chatId IN (...)` manually (2000 per call) as a flat top-level `WAMessage` query with `distinct: ["chatId"]` + `orderBy: [{chatId:"asc"},{timestamp:"desc"}]` (the standard Prisma "latest row per group" pattern), so it's never subject to Prisma's fragile relation-batching path no matter how many chats match. `CHAT_ATTRIBUTION_MESSAGE_QUERY` (still exported, unchanged) stays nested as-is in the other 3 call sites (`chats/route.ts`'s paginated inbox list, `lead-scores/route.ts`, `get-stats.ts`) — each bounded (page size, or the much smaller `WALeadScore` table) — but convert any of them to `fetchChatAttributions()` too the moment it starts returning thousands of unbounded rows.
- **Retention** (`lib/reports/retention.ts:purgeOldReports`): keeps the `REPORTS_RETENTION_COUNT` (default 20, env var) most recent `COMPLETED` reports, called at the end of every successful generation — no separate cron, unlike backups. Manual delete via `DELETE /api/reportes/[id]` always available (409s while `PENDING`/`RUNNING`).
- **Notifications**: `REPORT_READY`/`REPORT_FAILED` fire to every admin on completion/failure (`lib/workers/report-worker.ts:notifyReportResult`) — only on the job's *last* BullMQ attempt if it fails, since the job is safely retryable (read-only — see the `report-generate` row above).
- Env vars: `REPORTS_ROOT` (default `/app/reports`), `REPORTS_RETENTION_COUNT` (default 20).

## Webhook

`POST /api/whatsapp/webhook` handles Meta webhook. Key behaviors:
- Validates `X-Hub-Signature-256` **when `appSecret` is configured** on the matched account — rejects the payload if the HMAC doesn't match. `appSecret` is optional (Meta itself doesn't require it either); if an account has none set, signature validation is skipped for that account's payloads and the request is trusted based on the `phone_number_id` match alone. This is an intentional product decision, not a gap to close — don't "fix" it into a hard requirement without checking with the user first.
- Per-message logic (Contact upsert, chat upsert, `WAMessage` create, notification, bot enqueue, media-download enqueue, auto-assignment) lives in `lib/whatsapp/ingest-message.ts:ingestInboundMessage()`. The webhook route itself just parses Meta's payload shape and calls it per message. `ingestInboundMessage()` returns `{messageId, chatId} | null` (null = deduplicated by wamid).
- Maps all 4 Meta statuses to `WACampaignRecipient`: `sent → SENT`, `delivered → DELIVERED`, `read → READ`, `failed → FAILED`.
- Detects groups: `remoteJid.includes("@g.us")` → `isGroup = true`.
- For inbound media with a Meta `mediaId` and no local path yet, the webhook enqueues a `media-download` job (see Redis queues).
- **Subscribed webhook fields beyond `messages`**: `phone_number_quality_update`, `account_update`, `user_preferences` (configure these in each Meta App's WhatsApp product webhook alongside `messages`/`message_template_status_update` — `message_template_status_update` itself isn't consumed by the webhook; template status is instead refreshed both by the unattended `template-sync` queue tick (every 15 min, see "Redis + BullMQ") and by polling in `GET /api/whatsapp/templates` when the page loads, see "Creating templates for Meta"). Any other field arrives at the same URL and is silently ignored (`change.field` doesn't match any handled branch).
  - `phone_number_quality_update` and `account_update` are **not** per-message payloads — they carry no `metadata.phone_number_id`, only a phone number string (`display_phone_number` / `phone_number`) and the WABA id (`entry.id`). The account is resolved via `resolveAccountByWabaAndPhone()`: if exactly one `WAAccount` matches `wabaId`, it's used directly; if several accounts share that WABA, the reported phone number (digit-normalized) disambiguates. If neither is possible, the event is logged and dropped rather than guessed.
  - `phone_number_quality_update` updates `WAAccount.qualityRating`/`messagingTier`/`qualityUpdatedAt` (shown on the account detail page) and fires an `ACCOUNT_STATUS` notification only on a negative signal (rating/event matching `flag|downgrade|red|yellow`) — upgrades don't notify, only the badge updates.
  - `account_update` flips `WAAccount.status` to `ERROR` (with `errorMessage`) when the event or `ban_info` indicates a ban/restriction (`ban|disable|restrict|flag` in the event name); any other event still fires an informational `ACCOUNT_STATUS` notification without touching `status`.
  - `user_preferences` **is** per-number (carries `metadata.phone_number_id` like `messages`) and reports a lead opting out/in of marketing messages via WhatsApp's native mechanism (`category: "marketing_messages"`, `value: "stop"|"resume"`). Sets `Contact.optedOutMarketing`/`optedOutAt`. `campaign-worker.ts` excludes opted-out contacts from every future campaign send (marks the recipient `FAILED` with an explanatory `errorMessage` instead of calling Meta) — this doesn't affect manual/bot replies in an already-open chat, only campaign broadcast sends.
- **Message reactions**: a lead tapping an emoji reaction on a message arrives as its own entry inside the same `messages` array (`type: "reaction"`, `reaction: {message_id, emoji}` — `message_id` is the `wamid` of the message being reacted to, not this event's own `id`; `emoji` is empty/absent when the lead *removes* a reaction they'd previously set, not on the first reaction). It is **not** a message — `applyReaction()` (webhook route) filters it out of the batch before grouping/`ingestInboundMessage` and instead does a scoped `updateMany` writing straight onto `WAMessage.reaction` (nullable `String`) of the target row, keyed by `wamid` + `chat.accountId` (same cross-account defensiveness as `applyStatusUpdate`). Consequently a reaction never creates a bubble, never bumps `unreadCount`/fires a `CHAT_MESSAGE` notification, and never enqueues a bot job. WhatsApp only allows one active reaction per person per message, so the emoji simply overwrites — no ranking/ordering logic like `sent < delivered < read`. Rendered as a small chip anchored to the reacted bubble's outer corner in both the authenticated chat (`chat-workspace.tsx`) and the public read-only link (`public-chat-view.tsx`); the 5s poll in `chat-workspace.tsx` diffs `reaction` alongside `status`/`mediaUrl`/`transcription` when merging fresh data onto already-loaded messages — omitting it from that comparison would silently swallow reactions arriving on already-rendered messages until the chat is reselected/reloaded.

## Media handling

WhatsApp media is **binary-byte persisted locally on disk** (not just Meta URL references), so chat UI and bot vision can stream/read it without depending on Meta's short-lived (≈minutes) download URLs.

- **Storage**: `lib/whatsapp/media-store.ts` — `saveMediaFromMeta(accountId, mediaId, encryptedAccessToken)` (Meta fetch), `saveMediaFromBuffer(accountId, buffer, mimeType)` (persists a buffer already in memory — used for outbound Meta media uploads), `mediaReadStream(relativePath)` (fs stream), `resolveAbsolutePath(relativePath)` (with `..` traversal guard), `mediaEndpointFor(messageId)` (returns the proxy URL the UI must use). The pure helpers (`mediaEndpointFor`, `is*Mime`, `mimeTypeToExtension`) actually live in `lib/whatsapp/media-shared.ts` — a client-safe module with no `fs` imports that `chat-workspace.tsx` imports directly (importing `media-store.ts` from a client component would break the bundle); `media-store.ts` re-exports them for server consumers.
- **Path scheme**: `mediaUrl` stored on `WAMessage` is a path *relative* to `MEDIA_ROOT` (e.g. `<accountId>/<uuid>.<ext>`). All helpers accept/return relative paths; resolve to absolute only at the boundary.
- **Proxied serving**: `GET /api/whatsapp/messages/[messageId]/media` looks up the `WAMessage`, verifies access via `chatAccessWhere(session.user.id, session.user.role)` (same access rule as every other per-chat route, see "Architecture: roles" above — not a bare `getUserAccountIds()` membership check), streams bytes with `Content-Type: mimeType` and `Content-Disposition` (inline for image/audio/video, attachment for documents). Auth check is mandatory — without it any authenticated user could fetch any media by `messageId`.
- **Outbound upload (Meta only)**: `POST /api/whatsapp/media` accepts multipart `file` + `accountId`, validates account ownership (`getUserAccountIds()`) and that `phoneNumberId`/`accessToken` are set — it does **not** currently check `channel === "META_CLOUD"` explicitly, calls `uploadMedia(phoneNumberId, accessToken, file, name, mime)` (`lib/whatsapp.ts`, `POST /{phone_number_id}/media` Graph endpoint) which returns a Meta `mediaId`, then also persists a local copy for the outbound history. Rate-limited via `rateLimit()`. Returns `{ mediaId, mimeType, filename, localMediaPath, bytesSize }` to be passed to the send route as-is.
- **Chat composer** (`app/components/whatsapp/chat-workspace.tsx`) has a clip 📎 button (`Paperclip` icon, accent-color, left of the text input) that opens a hidden `<input type="file">` accepting `image/*,audio/*,video/*,application/pdf,text/plain`, max 20MB. Caption goes in the text input. The send flow is: upload → `/api/whatsapp/chats/[chatId]/send` with `{type, mediaId, mimeType, filename, localMediaPath, bytesSize, caption}`.
- **UI rendering**: `MessageBubble` switches on `messageType` (`image`/`audio`/`video`/`document`/`sticker`) and renders the appropriate tag pointing at `/api/whatsapp/messages/[id]/media`. While `mediaUrl` is null (async download still queued), shows a placeholder (`[imagen recibida]` etc.) — the 5s polling in the chat page picks up the populated row once the worker finishes. **Voice notes show their Gemini transcription** (`WAMessage.transcription`, italic text under the player) in both the workspace and the public `/c/[token]` view — persisted in the DB so it survives `media-cleanup` purging the audio file; the poll-merge "changed" check treats a new transcription as a row change so it appears without a reload.
- **Bot media input**: `lib/workers/bot-worker.ts:buildUserContent()` reads the inbound media's local bytes from disk → base64 data-URI part. Images → `image_url`; audio → `audio_url` (both via Gemini's native `inlineData`); documents → text extracted via `extract-document-text.ts` (PDF/`text/*`; other MIME types fall back to a label with the filename). Media in history turns is NOT forwarded (text-only) to bound token cost. `bot-worker` re-checks Prisma for `mediaUrl` if the enqueue payload's `localMediaPath` is empty (situation: bot job fired before `media-download` worker finished).

## WhatsApp Business Cloud API

Single channel today — `WAAccount.channel` is an enum (`WAChannel`) kept for future extensibility but only has one value, `META_CLOUD`. The `BAILEYS` channel (unofficial WhatsApp Web protocol, used for dev/testing without a public webhook URL) was removed: `lib/whatsapp-baileys/`, its API routes, and the `WABaileysSession` model are gone. `phoneNumberId`/`accessToken`/`wabaId`/`verifyTokenHash`/`appSecret` stay nullable on `WAAccount` because they're filled in during the account setup wizard, not because of a second channel.

- Outbound sends always go through `lib/whatsapp/send.ts:sendWhatsAppMessage(account, params)` (decrypts the token, delegates to `lib/whatsapp.ts:sendMessage()`) — keep using this wrapper from routes/workers rather than calling `sendMessage()` directly, so token decryption stays in one place.
- Template creation and bulk campaigns require `wabaId` + `accessToken` on the account (checked via `account.channel !== "META_CLOUD" || !account.wabaId || !account.accessToken` in `templates/route.ts`, `templates/create/route.ts`, `campaign-worker.ts` — the channel check is a no-op today but keeps the guard shape if a second channel ever comes back).
- **`WAAccount.appId`** — Meta App ID, distinct from `wabaId`. Only needed for the Resumable Upload API used when creating a template with a media (IMAGE/VIDEO/DOCUMENT) header — see `lib/whatsapp/resumable-upload.ts` and `POST /api/whatsapp/templates/upload-media`. Nullable/optional; accounts that only ever use text-header or headerless templates don't need it.

### Multiple numbers, each on its own Meta App

Every `WAAccount` is fully self-contained — `phoneNumberId`, `wabaId`, `accessToken`, `appSecret`, `verifyTokenHash`, `appId` — and every Graph API call site resolves these from the specific account row, never from a shared/global credential. There's no `META_APP_ID`-style env var and no assumption anywhere that all connected numbers belong to the same Meta App. Practical implications:

- When connecting a second (or Nth) number under a **different** Meta App, use that App's own App ID/App Secret/access token in "Agregar número" — don't reuse another account's values.
- All accounts share the same webhook URL (`/api/whatsapp/webhook`) — the system disambiguates inbound payloads by `phone_number_id` and the GET verification handshake by `verify_token` (both looked up per-account, see "Webhook" above), so multiple Meta Apps can point their WhatsApp product webhook config at the same URL without conflict.
- Manual steps on Meta's side that this system does **not** automate: in the new Meta App, set the WhatsApp product webhook to our URL + that account's generated verify token, and confirm the WABA is subscribed to that App's webhook (`POST /{waba-id}/subscribed_apps` — usually already done when the number was configured in Meta Business Manager, but worth checking first if inbound messages aren't arriving).

## CRM & team collaboration

- `Contact` (tags via `Tag`/`ContactTag`, `leadStatus`, notes via `WANote`) is auto-upserted per remote JID inside `ingestInboundMessage()` — one per `(accountId, remoteJid)`, 1:1 with `WAChat` via `WAChat.contactId`. Surfaced through `ContactDrawer` (`app/components/whatsapp/contact-drawer.tsx`) from both chat views and `/whatsapp/contactos`. **Name never regresses**: `lib/whatsapp/contact-name.ts:isFallbackName()` treats a name equal to the remote JID/phone number as "no real name" (consumed by `ingest-message.ts` via `shouldUpdateName()`, also from `contact-name.ts`) — `Contact.name`/`WAChat.name` only get overwritten with a new value if it's a real name or the existing one was itself a fallback, so a previously-learned name can't be clobbered by a later payload where Meta omits `profile.name`. `/whatsapp/contactos` also shows a Teléfono column (always) and a Cuenta column (only when the user has 2+ accounts).
- **Lead ID** (`lib/whatsapp/lead-id.ts`): every `Contact` carries a `leadNumber` (`BigInt`, 12 random digits) — deliberately generated by a Postgres column default (`@default(dbgenerated(...))`, not app code), since 3 separate call sites create `Contact` via `upsert` (`ingest-message.ts`, `campaign-worker.ts`, `lib/google/lead-sheet-import.ts`) and a DB-level default covers all three without touching any of them; it also means `prisma db push` backfills every pre-existing row for free, no migration script needed. Combined with `WAAccount.leadIdPrefix` (editable short code, e.g. `LM`) into a human-facing `LM-482913776521` via `formatLeadId()` — falls back to `suggestLeadPrefix(account.name)` (deterministic, first 3 letters) when the account has no explicit prefix set. `leadIdPrefix` is intentionally **not** `@unique` — several accounts can share one prefix on purpose to group them under one brand, since uniqueness of the visible ID is already guaranteed by `leadNumber` alone. Exposed today only as the "ID de lead" column in the `LEAD_SCORES` export (`lib/whatsapp/export-columns.ts`) — CSV and Google Sheets share the same column definitions, so it's available in both automatically, but a `SheetExport` created before this column existed needs the checkbox added manually to its saved `columns` list. `leadNumber` is a `BigInt` — always convert to `string` before it crosses a `NextResponse.json()` boundary (see the two `LeadScoreRow` builders, `app/api/whatsapp/lead-scores/route.ts` and `lib/google/dataset-queries.ts:buildLeadScoreRows`) or it throws at serialization time.
- Chat assignment: `WAChat.assignedToId` restricted to the account owner + `WAAccountShare` grantees (`lib/chat-assignees.ts:getEligibleAssignees()`, the shared candidate pool used everywhere assignment/mentions/auto-assign need "who can touch this account"). Assigning manually triggers no side effect by itself; a `CHAT_MESSAGE` notification fires on the *next* inbound message if the chat is already assigned (or gets auto-assigned, see below).
- `Notification` model + polling bell (`app/components/ui/notification-bell.tsx`, polls `GET /api/whatsapp/notifications` every 25s). `NotificationType` (12 values): `CHAT_MESSAGE`, `CAMPAIGN_COMPLETED`, `CAMPAIGN_FAILED`, `BOT_ERROR`, `BUDGET_EXCEEDED`, `ACCOUNT_STATUS` (webhook `account_update`/`phone_number_quality_update`, see "Webhook"), `SCORER_ERROR` (scheduled scorer failed every chat in its last run), `SYSTEM_ISSUE` (hourly `system-diagnostics` tick, see "Redis + BullMQ"), `BACKUP_COMPLETED`/`BACKUP_FAILED`, `RESTORE_COMPLETED`/`RESTORE_FAILED` (see "Backups & disaster recovery"). No websockets in this app — polling is the established pattern for anything "live."
- Monthly AI budget: `AppSettings.monthlyBudgetUsd` (optional) + `budgetAlertMonth` (guards against re-notifying within the same month). Checked in `bot-worker.ts` after every logged `WABotUsage` row. **All AI consumers gate on `isMonthlyBudgetExceeded()` before spending**: lead-scoring and lead-recovery skip their tick, `bot-worker.ts` skips the reply (logs, no `ERROR` status — it's not a bot failure) and `audio-transcribe-worker.ts` skips the transcription once the budget is spent. `getMonthlyAiCost()` sums `WABotUsage` + `WALeadScorerUsage` + `WALeadRecoveryAttempt` + `AgentUsage` + `AudioTranscriptionUsage` — any new usage source extends that aggregate, not a parallel check.
- **Blacklist ("solo automatización", `Contact.blockedAt` + `blockedNote`)**: blocking a contact stops the bot (ingest skips the bot enqueue; `bot-worker` re-checks as a second line of defense), lead-recovery, lead-scoring (shared guard in `scoreChatWithScorer` + candidate-query filters), campaigns (worker marks recipients `FAILED` like opted-out; creation pre-filters them via `app/api/whatsapp/campaigns/route.ts`) and Sheets import (row marked `skipped`). Their messages are **still stored, notified and manually replyable** — the block is against machines, not humans. Per-account (same shape as `optedOutMarketing`; same person on two accounts = two independently blockable contacts). Toggle via `POST /api/whatsapp/contacts/[id]/block` (`{action: "block"|"unblock", note?}`, access via `getUserAccountIds()`, rate-limited); UI in the ContactDrawer + "Bloqueado" badges in `/whatsapp/contactos` and the chat list. **Campaign opt-out/blocked matching is done by phone digits** (strips `@s.whatsapp.net`): the old opt-out Set compared `remoteJid` against the digits-only recipient number and never matched webhook-created contacts — both checks now normalize. Not folded into `chatAccessWhere()` on purpose: visibility stays intact (even for admins), blocking is a behavior filter, not a visibility one.
- **Campaign sends create CRM records**: a successfully delivered campaign recipient now upserts a `Contact`/`WAChat`/`WAMessage` (`direction: OUTBOUND`, `messageType: "template"`) and tags both the contact and chat with `Campaña: <campaign name>` (`lib/workers/campaign-worker.ts`) — so campaign leads show up in `/whatsapp/contactos` and the chat list, not just in `WACampaignRecipient`. A recipient that fails to send leaves no CRM trace (no phantom contact). `WAMessage.body` for this record holds the real rendered template text (`lib/whatsapp/template-variables.ts:renderTemplateText()`, substitutes `{{n}}` the same way `<TemplatePreview>` does for display), and `WAMessage.campaignId` (FK to `WACampaign`) attributes the message so `bot-worker.ts` can inject a one-line "this chat started from campaign X, template Y" system note when the most recent outbound message in the chat came from a campaign — regardless of `bot.memoryType`. A campaign's image/video header is persisted locally **once per campaign** (not re-downloaded per recipient) and each recipient's `WAMessage` points at that copy, so the header renders in the chat via the same `<MediaContent>`/media-proxy path as any other media.
- **Campaign template variables** (`whatsapp/campanas/nueva/page.tsx`): `lib/whatsapp/template-variables.ts:getTemplateVariables(components)` (shared by the UI and `campaign-worker.ts`) inspects a template's raw Meta `components` JSON to detect what needs a value — body `{{n}}` count (per-recipient, `WACampaignRecipient.parameters`), header text/media (campaign-wide, `WACampaign.headerParam` — media headers hold a Meta message-media `id`, uploaded via `/api/whatsapp/media`, not a URL), and a URL button's dynamic suffix (campaign-wide, `WACampaign.buttonParam`). Footer never has variables in Meta's template model. The worker resolves the button's array index from the template's own `BUTTONS` component so the `sub_type: "url"` component always targets the right button.
- **Recipient CSV import** (`lib/whatsapp/parse-csv.ts`) expects a header row (`telefono`/`nombre` recognized by name, any other columns become body parameters in file order) and shows a read-only, paginated (10/page) preview via the shared `<Table>` — imported rows are kept in a separate array from manually-typed rows rather than rendered as hundreds of editable inputs.

### Lead scoring (`WALeadScorerBot` / `WALeadScore`)

Distinct from the AI reply bots (`WABot`): a `WALeadScorerBot` (own `name`/`provider`/`model`/`systemPrompt`, CRUD at `/whatsapp/calificadores`) scores a *conversation transcript* on demand rather than replying to it. `POST /api/whatsapp/chats/[chatId]/score` requires a `scorerId` in the body, loads that scorer's config + the chat's messages, and asks the AI for `{score (0-100), label: "frio"|"tibio"|"caliente", summary, reasons[]}` via a fixed JSON-contract system message appended after the scorer's own system prompt. The result is upserted on `@@unique([chatId, scorerId])` — **a chat can carry one score per scorer**, not a single global score; don't assume `WALeadScore` is 1:1 with `WAChat`. `GET` on the same route returns all scores for the chat (one per scorer that has run so far). `GET /api/whatsapp/chats/[chatId]/scorers` lists the account owner's active scorers for the picker. `LeadScoreBadge` (popover in the chat header) lets the user pick a scorer, re-run it, and flip between scorers' past results.

The actual scoring logic (transcript build, AI call, JSON parse, `WALeadScore` upsert, usage logging) lives in `lib/whatsapp/lead-scoring.ts:scoreChatWithScorer(chatId, scorer)`, shared by both the manual "Calificar" button and the scheduled tick worker below — don't duplicate this logic inline in a route handler.

`/whatsapp/calificadores` has two in-page tabs (client-side `useState`, same idiom as `bots/[id]/page.tsx`): **Calificadores** (CRUD list; hidden entirely for role `user`, see roles) and **Leads calificados** (`GET /api/whatsapp/lead-scores`, all `WALeadScore` rows across the user's accounts) — the latter is the cross-chat view of everything any scorer has produced so far. The Leads tab filters client-side by scorer/label/account/phone/date range, paginates client-side (`<Pagination>`, slice over the filtered array), opens a per-lead detail modal, and exports CSV via a column/scope-picker modal (`lib/csv.ts:toCsv()/downloadCsv()` — reuse these for any new CSV export).

Beyond `{score, label, summary, reasons[]}`, the JSON contract asks for a structured `details` object (buying signals, objections, next steps, product of interest — the 5-phase methodology prompt in `lib/whatsapp/lead-scoring.ts` dictates its shape), persisted as `WALeadScore.details Json?` — a flexible blob on purpose, don't normalize it into columns.

**Scheduled/periodic scoring**: `WALeadScorerBot.scheduleEnabled` + `scheduleIntervalMinutes` (one of `LEAD_SCORER_SCHEDULE_INTERVALS` in `lib/validations.ts` — 15/30/60/180/360/720/1440) + `scheduleAccountIds` (`String[]`, empty = all the owner's accounts) let a scorer re-run itself unattended instead of only via the manual button. A single BullMQ repeatable job (`lead-scoring` queue, `lib/workers/lead-scoring-worker.ts`, cron `*/5 * * * *`, registered in `lib/workers/index.ts`) ticks every 5 minutes — the shortest resolution needed since 15 min is the smallest selectable interval — and for each due scorer (`now - lastRunAt >= scheduleIntervalMinutes`) re-scores up to 15 of its owner's `OPEN`/`PENDING` chats that either have never been scored by it or have new messages since the last score (`WAChat.lastMessageAt > WALeadScore.updatedAt`), then stamps `lastRunAt`. Before running, it checks `isMonthlyBudgetExceeded()` (`lib/ai/budget.ts`) and skips the whole scorer for that tick if the user's monthly AI budget is already spent — unattended runs don't get to blow through a budget the way a human clicking a button implicitly self-limits.
- **Usage/cost tracking**: unlike the original manual-only flow, every scored chat now logs a `WALeadScorerUsage` row (mirrors `WABotUsage` — tokens + `estimatedCost`), and `lib/ai/budget.ts:getMonthlyAiCost()`/`checkBudgetAlert()` sum **both** `WABotUsage` and `WALeadScorerUsage` — the monthly budget and the `BUDGET_EXCEEDED` notification reflect total AI spend, not just reply-bot spend. `lib/estadisticas/get-stats.ts`'s `totalCost`/`totalTokens`/`monthlyCost` were updated the same way. If you add a third kind of AI usage in the future, extend `getMonthlyAiCost()` rather than adding a parallel budget check.

### Lead recovery (`WALeadRecoveryAttempt`)

Autonomous re-engagement of leads that went silent ("en visto"). Config lives **per user** on `AppSettings` (`leadRecoveryEnabled` — default `false`, `leadRecoveryFirstMessageHours`/`leadRecoverySecondMessageHours` (`null` = only 1 attempt), business-hours window `leadRecoveryBusinessHourStart/End` + `leadRecoveryTimezone`), edited from the admin-only `/configuracion/ia` page. The `lead-recovery` queue ticks every 15 min (`lib/workers/lead-recovery-worker.ts:processLeadRecoveryTick()`):

- Per enabled user: skips the whole tick if `isMonthlyBudgetExceeded()` or outside business hours (checked in the user's configured timezone).
- Candidates: `OPEN`/`PENDING` chats across `getUserAccountIds()` whose **last message is OUTBOUND** and that have at least one INBOUND message ever (a campaign recipient who never replied is not an "abandoned" lead). Bounded per tick: `CANDIDATE_POOL = 200`, `BATCH_SIZE = 20` sends max.
- Attempt logic: hours of silence measured from the lead's last inbound; `WALeadRecoveryAttempt` rows created *after* that inbound count as attempts (so a lead who replies resets the sequence). Max 2 attempts.
- The message is **generated by the account's active `WABot`** (`lib/whatsapp/lead-recovery.ts:sendRecoveryMessage()` — coherent with the conversation, wrapped prompt + `SCOPE_GUARDRAIL`); accounts without an active bot are skipped.
- **Meta 24h window**: only free-text messages inside Meta's 24h customer-service window (from the lead's last inbound) are sent — past 24h it sends nothing (no reactivation template configured yet).

This runs unattended and messages real leads — treat `leadRecoveryEnabled` and the hour thresholds as production-sensitive settings; never flip them in the DB while testing without telling the user.

### Conversation-level features (distinct from Contact-level)

These mirror equivalent Contact-level concepts but are **separate models** scoped to the `WAChat` itself, not the underlying lead/contact — don't conflate them:

- **`WAChat.status`** (`ChatStatus`: `OPEN`/`PENDING`/`RESOLVED`, default `OPEN`) + `resolvedAt` (set when transitioning to `RESOLVED`, cleared on reopen). The chat header's status picker was removed 2026-08 (unused in practice — every chat in production was still sitting at the `OPEN` default, nobody had ever moved one to `PENDING`/`RESOLVED`), so nothing in the UI changes this field anymore; `PATCH /api/whatsapp/chats/[chatId]/status` and the Asistente IA's `chatsStatusSet` tool still exist and work, just with no UI entry point. Consequently `lib/estadisticas/agent-performance.ts`'s `resolvedCount`/`avgResolutionMinutes` columns will read `0`/`—` going forward — known, accepted trade-off, not a bug. `GET /api/whatsapp/chats` still supports `?status=` (comma-separated), but the inbox no longer renders status tabs — they were removed along with the whole `WAChatNote` internal-notes feature (model, routes, drawer, `@mention` parsing and the `NOTE_MENTION` notification type all deleted for lack of use; `WANote` on Contact remains). Don't re-introduce any of this without asking.
- **Inbox filters** (`chat-workspace.tsx`): campaign (`?campaignId=`, a relation filter on `WAMessage.campaignId` — not the `Campaña: X` text tag) and lead-reply (`?hasReplied=yes|no`). Each chat row shows a campaign badge (most recent campaign-tagged message) with a hash-derived tone. The `/whatsapp/chat` area renders **full-bleed** — `app-shell.tsx` drops the standard page padding + breadcrumb when `pathname.startsWith("/whatsapp/chat")` (`h-svh`, internal scroll).
- **Per-chat AI cost**: `GET /api/whatsapp/chats/[chatId]/usage` returns the per-interaction list (bot replies + scorer runs — `WABotUsage` + `WALeadScorerUsage` by `waChatId`) with model/tokens/`estimatedCost`; surfaced as a cost badge with breakdown in the chat header. It's per *AI call*, not per message (a humanized reply spans several `WAMessage` chunks from one call).
- **`ChatTag`** (bridge table, same shape as `ContactTag` but for `WAChat`) reuses the global `Tag` catalog and `/api/whatsapp/tags` GET/POST as-is. Chat-scoped CRUD at `/api/whatsapp/chats/[chatId]/tags`, UI in `chat-tag-picker.tsx` (popover in the chat header, *not* a drawer).
- **`CannedResponse`** (per-`waAccountId`, `shortcut` + `content`, shared across everyone with access to that account) — managed from the "Respuestas rápidas" section embedded in `/configuracion` (`configuracion/_respuestas-rapidas.tsx` + its `_respuestas-rapidas-form.tsx` modal; the old standalone `/configuracion/respuestas-rapidas` page was folded in during the 2026-07 nav flattening). In the chat composer, typing `/shortcut` filters and shows a dropdown; Tab or click inserts the full `content`.
- **Auto-assignment** (`lib/whatsapp/auto-assign.ts:autoAssignChat()`) — opt-in per account via `WAAccount.autoAssignEnabled` (toggle on the account detail page), off by default so it never silently changes existing manual-assignment behavior. When enabled, an unassigned inbound message is routed to the eligible candidate (`getEligibleAssignees()`) with the fewest `OPEN`/`PENDING` chats, respecting `User.maxOpenChats` (`null` = unlimited; candidates at their cap are skipped). Wired into `ingestInboundMessage()` right before the `CHAT_MESSAGE` notification check.
- **Per-agent metrics**: `WAMessage.senderId` records which human sent a manual outbound reply (set in `chats/[chatId]/send/route.ts`; bot replies leave it `null` — bots are tracked separately via `WABotConversation`). `WAChat.firstResponseAt` is stamped the first time a manual reply is sent on a chat. `lib/estadisticas/get-stats.ts` aggregates these (in JS, not SQL — Prisma can't `AVG()` a date difference) into `agentPerformance` (resolved count, avg minutes to first response, avg minutes to resolution), rendered in `estadisticas/_view.tsx`.
- **Public read-only chat link** (`WAChat.publicShareToken`, nullable/unique, never set on chat creation): a link to `/c/[token]` — a login-free, read-only view of the conversation (text + full media playback/download), with no composer and no navigation into the protected app. Generated on demand (button in the chat header, `chat-public-link-button.tsx` → `POST/DELETE /api/whatsapp/chats/[chatId]/public-link`, auth-gated via `chatAccessWhere()` same as any other per-chat route) and revocable at will — revoking just nulls the column, a later regenerate mints a brand-new token, the old URL dies permanently. `lib/whatsapp/chat-public-link.ts` owns token generation (`ensurePublicChatToken` single, `ensurePublicChatTokensForChats` bulk) and `publicChatUrl()` (absolute URL, built from `NEXT_PUBLIC_APP_URL` — must be set in prod or the link comes out with an empty domain). `/c` is deliberately **outside** `PROTECTED` in `proxy.ts` (no session check) and outside `(dashboard)` (own minimal `app/c/layout.tsx`, no sidebar). Data comes from `lib/whatsapp/public-chat-data.ts:getPublicChatData()`, shared by the page (Server Component, no extra roundtrip) and `GET /api/public/chat/[token]` (rate-limited by IP, for any future client-side refresh); media streams from `GET /api/public/chat/[token]/media/[messageId]`, which re-validates the message belongs to that exact token's chat rather than trusting the id alone. The token is also what makes the **"Link público del chat"** column in `EXPORT_COLUMNS` (`export-columns.ts`) work — both `GET /api/whatsapp/lead-scores` (CSV export) and `buildLeadScoreRows` (`dataset-queries.ts`, Sheets sync) call `ensurePublicChatTokensForChats()` before building rows, since a chat can carry several `WALeadScore`s (one per scorer) that must all resolve to the *same* link.

## Design system

All tokens in `app/globals.css` as CSS custom properties. Accent: refined WhatsApp green (`#22C55E` dark, `#15803D` light — evolved from the original flatter `#25D366`/`#1ea952` to feel less like a literal WhatsApp clone while keeping the brand association). **Neutrals are warm (2026-07 "Conversación primero" redesign)**: dark surfaces are warm charcoal (`#14120f` family, earthy hue — the green lives only in `--accent`), light surfaces warm cream/gray (`#faf9f5`/`#f3f0e9`). `success` stays teal (`#2dd4bf` dark / `#0d9488` light) so it reads distinct from `accent` — don't let them drift back to the same hue.

**Redesign identity elements** (apply with restraint, they're the signature — not defaults):
- **Bubble corner**: `rounded-bubble` (small corner bottom-left) / `rounded-bubble-br` (bottom-right), defined as `@utility` in `globals.css`. Whitelist: `EntityAvatar`, primary `Button` variant, active sidebar item, own chat bubbles. Don't spread it to arbitrary surfaces.
- **Per-entity hue**: 8 `.hue-0`…`.hue-7` classes set `--entity`/`--entity-bg` (oklch, light/dark aware, hues avoid accent-green ~150° and success-teal ~180°), consumed via `bg-entity`/`text-entity`/`bg-entity-bg` utilities. **Only** assign via `HUE_CLASS[hueIndex(id)]`/`hueClassFor(id)` from `app/components/ui/hue.ts` (hash keyed by `accountId` so one WhatsApp number = one color everywhere) — never interpolate `hue-${n}`.
- **Type scale**: `text-hero` (2.75rem, hero numbers), `text-page-title` (h1, rendered in Fraunces via `PageHeader`), `text-eyebrow` (section eyebrows). Every figure/phone/date/metric renders in `font-mono` (IBM Plex); Fraunces (`font-display`) is for page titles and section headings only.

**Never** write inline button/card/input classes. **Never** use Tailwind color literals. Use semantic tokens: `text-accent`, `bg-surface`, `text-muted`, `text-success`, etc.

Form pattern: `<FormField label="…" error={…}>{(id) => (<Input id={id} … />)}</FormField>`

Toast: `const { success, error } = useToast()` → `success("text")`

Three select flavors in `app/components/ui/` — pick by need, don't build a fourth: `select.tsx` (styled native `<select>`, short lists), `multi-select.tsx` (checkbox multi-select), `searchable-select.tsx` (`SearchableSelect`, single-select combobox with a search input that only starts filtering at ≥3 chars — below that the full list stays visible; used for long lists like the template picker in `campanas/nueva`). `pagination.tsx` (`<Pagination currentPage totalPages onPageChange>`) is the shared pager for client-side paginated lists.

### Layout: workbench (overview pages) + `EntityList` (entity lists)

The 2026-07 redesign replaced the old BentoGrid/TileGrid tile system (deleted: `bento-grid.tsx`, `tile-grid.tsx`, `stat-card.tsx`, `SkeletonCard`) with an editorial "workbench" layout. Primitives, all in `app/components/ui/`:

- **`kpi-strip.tsx`** (`KpiStrip`, `KpiItem`) — single dense row of KPIs with vertical dividers, no boxes/icons. Values are pre-formatted strings in `font-mono`; `delta?`/`deltaTone?` for secondary figures, `href?` wraps the cell in a `Link`, `size="hero"|"compact"`. **Deliberately server-safe and icon-free**: no icon props means RSCs (`dashboard/page.tsx`) use it directly without hitting the "functions cannot be passed to Client Components" error.
- **`section-header.tsx`** (`SectionHeader`) — eyebrow (uppercase `text-eyebrow`) + Fraunces title + optional `action` ReactNode. Sections separate by typography, not bordered cards. Server-safe.
- **`workbench.tsx`** (`Workbench`/`WorkbenchMain`/`WorkbenchAside`) — the `lg:grid-cols-3` editorial split (main 2/3 + aside 1/3, collapses to 1 col below `lg`). Server-safe.
- **`avatar.tsx`** (`EntityAvatar`) — initials avatar, `rounded-bubble`, hue keyed by `id` (pass `accountId` for anything WhatsApp-scoped so one number = one color across inbox/lists/overviews). Server-safe.
- **`entity-list.tsx`** (`EntityList` + `EntityRow`, `"use client"`) — dense database-style rows replacing TileGrid on entity list pages (Contactos, Plantillas, Bots, Campañas ×2 tabs, Usuarios). **Same contract TileGrid had** (`rows`/`rowKey`/`loading`/`error`/`onRetry`/`emptyIcon`/`emptyTitle`/`emptyDescription`/`emptyAction`/`onRowClick`/`rowActions`, reusing `ListErrorState`/`EmptyState`/`SkeletonRow`), with `renderTile`→`renderRow` and no `columns`. `rowActions` renders inside the same `Dropdown`+`stopPropagation()` pattern, revealed on hover/focus on `md:+` and always visible on touch. For inline (non-dropdown) per-row actions, return a fragment from `renderRow`: `<><EntityRow …/><span onClick={stopPropagation}>…buttons…</span></>` (see Bots/Usuarios/Campañas). `EntityRow` gives the standard anatomy: `leading` (usually `EntityAvatar`), `title`, `subtitle`, `badges`, `meta` (right-aligned, hidden below `sm`, figures in `font-mono`). No sort headers — pages needing ordering keep a toolbar `<Select>`.

Overview page shape (see `dashboard/page.tsx`, `estadisticas/_view.tsx`): `PageHeader` → `KpiStrip` → `Workbench` with `SectionHeader`-separated sections; entry stagger via `animate-fade-in-up` + `animation-delay-100..400`. `loading.tsx` files mirror the same skeleton shape — update them in the same change as their page.

**Form/detail pages center their narrow content**: single-column pages (`campanas/nueva`, `campanas/automatizacion/nueva`, `campanas/[id]`, `bots/[id]`, `cuentas/[id]`, `configuracion/**`) wrap everything in `max-w-{2xl|3xl|4xl} mx-auto` — a left-pinned narrow column leaves the right half of wide screens dead. The `mx-auto` is mandatory whenever a page root sets a `max-w-*`; text inside stays left-aligned.

`table.tsx`/`<Table>` is **not deprecated** — still the right tool for dense multi-column numeric reports; used inside workbench sections in `estadisticas/_view.tsx` (campaign breakdown, bot usage, agent performance).

`app/components/ui/page-header.tsx` (`title`/`description`/`actions`) renders the h1 in `font-display text-page-title` (Fraunces). Use it on every top-level list/dashboard page; detail pages with a back-link (`bots/[id]`, `campanas/[id]`, `cuentas/[id]`) keep their own back-link + heading instead.

**Chat rail**: `chat-workspace.tsx`'s conversation rail keeps its own dense inbox structure (not workbench/EntityList) — the 2026-07 redesign only skinned it: `EntityAvatar` per row, hue-colored group headers with an `animate-pulse-live` dot, own bubbles in `rounded-bubble-br`. Structure/polling/composer untouched — still confirm with the user before restructuring it.

### Create/edit modal pattern

Standard entity CRUD lives in a `_form.tsx` file next to the list's `page.tsx`, exporting a single `<XxxFormModal open onClose onSaved initialData? />` that handles both create and edit (`initialData` present ⇒ edit). Structure: `<Modal size="md|lg|xl" footer={Cancelar/Guardar}>` + `{error && <Banner tone="danger">}` + `<FormField>` blocks. See `whatsapp/plantillas/_form.tsx` as the reference implementation.

Exceptions that stay as a dedicated page instead of a modal:
- Unbounded dynamic content (`whatsapp/campanas/nueva` — recipient list can grow to hundreds of rows via CSV import; doesn't fit a modal's `max-h-[90vh]`).

Account creation (`whatsapp/cuentas/_form.tsx:CuentaFormModal`) follows the standard modal pattern but has a two-step render: the create form, then (on success) a read-only "here are your values" step showing the webhook URL and the auto-generated verify token — `verifyToken` is never typed by the user and never stored in plaintext (`WAAccount.verifyTokenHash` only), so that success step is the *only* place it's ever visible. External entry points link to `/whatsapp/cuentas?nueva=1`, which auto-opens the modal (`cuentas/page.tsx` reads the `nueva` search param into the modal's initial `open` state — wrapped in `<Suspense>` per the `useSearchParams()` rule above).

## Gotchas summary

- **`npm run build` inside the dev compose fails with `TypeError: Cannot read properties of null (reading 'useContext')` while prerendering** — `docker-compose.override.yml` sets `NODE_ENV=development`, which poisons the production build (dev React mixed into SSR chunks). It is NOT a code bug: run the build check as `docker compose run --rm -e NODE_ENV=production app sh -c "rm -rf .next && npm run build"`, then `docker compose run --rm -u root app sh -c "rm -rf .next"` + `docker compose up -d app` so the dev server doesn't boot on the production `.next`. **Caveat**: `docker compose run --rm` starts a brand-new container from the *image*, whose `/app/node_modules` is an anonymous volume seeded from whatever the image had at last build — if you just `npm install`ed a new package into the live running container without rebuilding the image, that `run --rm` won't see it ("Module not found"). Use `docker compose exec -e NODE_ENV=production app sh -c "rm -rf .next && npm run build"` instead (reuses the already-running container's up-to-date `node_modules`), then still restart the dev server after (it shares the same `.next` dir as the live `npm run dev` process, so a build attempt run via `exec` mid-session leaves it in a half-rebuilt state until you `docker compose restart app`).
- **Next dev blocks cross-origin requests to dev-server internals (HMR, RSC payloads) from any hostname other than `localhost`** — accessing the dev server (`:17100`) from another machine (LAN IP, Tailscale hostname, ngrok tunnel) silently breaks navigation/HMR unless that hostname is in `next.config.ts`'s `allowedDevOrigins` array. Symptom looks like "login/navigation just doesn't complete" from the other machine, works fine from `localhost` on the host itself. Add the hostname to the array and `docker compose restart app` (config changes aren't hot-reloaded). Irrelevant in production (`next start`, not `next dev`). See "Development" above for how to determine this machine's own hostname/MagicDNS name in local mode.
- **Campaign visibility is per account, not per creator** — `GET /api/whatsapp/campaigns`, the `[id]` detail/DELETE and `send` all filter by `waAccountId ∈ getUserAccountIds()`; a `WAAccountShare` grantee can create/see/send campaigns on the shared account and the owner sees them too. Don't regress these back to `userId: session.user.id`.
- **Role guards live in the APIs too, not just `proxy.ts`** — all `/api/whatsapp/bots/**` handlers 403 for any non-admin, and `GET /api/whatsapp/contacts` (the list) 403s for role `user` (the `contacts/[id]` detail stays open — the chat's ContactDrawer needs it). `PATCH /api/usuarios` refuses to demote the first-created admin or the last remaining admin.
- **Empty `public/` kills Docker build** — must have `.gitkeep`
- **`tailwindcss` in deps, not devDeps** — production builds need it
- **`hideUnattributedChats` filters lists, not counters** — `countChats()` in `lib/estadisticas/global-counts.ts` (Panel + Estadísticas) and `get-stats.ts` still count hidden chats, so a restricted role can see "120 chats" as a KPI while their inbox lists 3. No content leaks (they're bare numbers), but if you align them, extend `global-counts.ts` rather than filtering inline per screen.
- **Shared accounts** — any route resolving a `WAAccount` from user input must check membership via `getUserAccountIds()`, **never** `findFirst({ id, userId: session.user.id })` — the latter 404s ("Cuenta no encontrada") for users who got the account via `WAAccountShare`. This exact bug shipped three times (template sync, template create, campaign create) before being fixed; grep for `userId: session.user.id` next to `wAAccount` when touching account-scoped routes.
- **Never nest `CHAT_ATTRIBUTION_MESSAGE_QUERY` inside a `select`/`include` on a `findMany` that can return many rows** — Prisma loads that filtered to-many relation (negation filters `campaignId`/`leadSheetSourceId` `not: null`) via a separate batched `chatId IN (...)` query it can't auto-split when negation is involved, and throws "Query parameter limit exceeded" once the parent result set hits the thousands (see "Reportes" → `fetchChatAttributions()` gotcha). Use `fetchChatAttributions(chatIds)` (`lib/whatsapp/chat-attribution.ts`) instead for any new route/builder whose result set isn't tightly bounded (pagination, a small table).
- **Knowlege index is async** — use `ragQueue.add()`, never `indexDocument()` directly in HTTP handlers
- **RAG chunk IDs** — use `crypto.randomUUID()`, not `Date.now()`
- **Template creation** — `wabaId` must exist on the account; templates require Meta review
- **Campaign templates** — API must validate `status: "APPROVED"` in addition to existence
- **Embeddings** — dimension is 768, not 1536 (changed from original schema)
- **Rate limiting** — add `rateLimit()` to any new auth-sensitive endpoint
- **Catch blocks** — use `toastError()` not empty `{}` in client code
- **`cn()`** — simple join, no tailwind-merge (avoids Docker dep issues)
- **`login` page** — uses `Suspense` boundary for `useSearchParams("callbackUrl")`
- **Startup script** — uses `migrate deploy` when `prisma/migrations/` exists, falls back to `db push`. This repo currently has **no** `prisma/migrations/` directory — always use `npx prisma db push`, not `migrate dev`, for schema changes.
- **Dev container needs a restart after `prisma db push`** — the running `npm run dev` process keeps the pre-regeneration Prisma Client in memory; `npx prisma generate` writes new files to `node_modules` but the live process won't pick them up without `docker compose restart app` (or a full `down -v && up --build`). Queries against newly-added models/fields will 500 until restarted.
- **`WABot.status` vs `isActive`** — two separate gates. `ingestInboundMessage()`'s bot lookup requires *both* `isActive: true` and `status: "ACTIVE"`. Any unhandled error in `processBotMessageJob()` sets `status: "ERROR"` (and notifies) — toggling `isActive` back on via `POST /api/whatsapp/bots/[id]/toggle` is what resets `status` back to `"ACTIVE"`; the bot won't recover just by looking "Active" in a stale UI state. The test-conversation endpoints (`/test/conversations/**`) also bypass both fields entirely (they only check bot ownership + admin role) — testing can succeed while the real message pipeline stays silently dead. Since 2026-07 they share the real `generateBotReply()` (RAG/tools/guardrails included, see "Bot tool-calling" under AI providers), so this gap is narrower than it used to be, but `isActive`/`status` still aren't part of what it checks.
- **`WABot.waAccountId` is nullable** — a bot can be created and exercised via its `/test` ("Probar") tab without a WhatsApp account attached; it just never gets picked up by the real inbound pipeline (which filters by account) until one is assigned.
- **`WALeadScore` is keyed by `(chatId, scorerId)`, not just `chatId`** — a chat can carry scores from multiple `WALeadScorerBot`s at once; `findUnique({where:{chatId}})` no longer works, use the composite key.
- **`pdf-parse` must be imported as `pdf-parse/lib/pdf-parse.js`** (the inner module), never the package root — the root `index.js` has a top-level debug block gated on `!module.parent` that misfires under ESM dynamic import and crashes trying to read a bundled test fixture. See `lib/whatsapp/extract-document-text.ts`.
- **`leadRecoveryEnabled` sends real WhatsApp messages unattended** — the `lead-recovery` tick fires every 15 min regardless of app restarts. Never enable it (or shrink its hour thresholds) in a dev DB pointing at real accounts without the user's explicit OK.
- **`MEDIA_RETENTION_DAYS`** (default 90) drives the daily `media-cleanup` queue job that deletes old `WAMessage` media files — set to `0` (or leave unset with a non-positive value) to disable purging.
- **pgvector IVFFlat index** — see "pgvector" under Database; don't re-add the `CREATE INDEX` to `docker/init.sql`, it will silently no-op there.
- **BullMQ repeat patterns need `tz: MEXICO_CITY_TZ`** — see "Zona horaria (CDMX)" above; omitting it silently shifts a cron tick to UTC wall-clock instead of CDMX.
- **Never put `<Button>` inside `<Link>`** — renders invalid HTML (`<button>` inside `<a>`). Instead: `<Button onClick={() => router.push("/path")}>` or use a plain `<a>` styled as a button.
- **`/api/whatsapp/chats` has two response shapes** — a flat array (legacy, when called with no `page` query param — no in-app consumer left since the overviews became RSC/Prisma-direct, but the shape survives for compatibility) vs. `{items, total, page, pageSize}` (when `page` is present — how `chat-workspace.tsx` calls it). Check which shape a new consumer needs before adding a call.
- **Playwright browser not installed in this environment** — `mcp__plugin_playwright_playwright__*` tools fail with "Chromium distribution 'chrome' is not found" until `npx playwright install chrome` is run; don't assume visual/browser verification is available without checking first. **However**, the plain `mcp__playwright__*` / `mcp__playwright-auth__*` tools (no `plugin_` prefix) work fine and were used successfully this session for real browser verification (login, click-through, file upload, screenshots) — check which namespace is actually available before assuming browser testing is off the table.
